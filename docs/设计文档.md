# 蝉蜕（Chrysalis）

> Mac 视频转码工具。名字取意「金蝉脱壳」——转码即蜕变：旧壳留在身后，本体无损，飞向新形。
> 本文是 v1 规划，不是最终 API 设计。

## 结论

技术路线定为：

**SwiftUI 界面 + AVFoundation 解封装/解码 + VideoToolbox 硬件编码 + AVAssetWriter 封装。**

不引入 FFmpeg、libav 或任何第三方转码库。硬件加速是硬性要求：默认强制使用 VideoToolbox 硬件编码器，没有对应硬件编码器时直接报错，不静默回退软件。

这个约束决定了能力边界：**只支持 AVFoundation 能读、VideoToolbox 能编的格式**。MKV/AVI/FLV/WMV 输入、AV1/VP9 编码、复杂字幕、Dolby Vision 都不在 v1 范围内。

电影元数据单独走一条轻量链路：**URLSession + Codable 调 TMDB → 人工确认/勘误 → 写入 MP4/MOV 容器 metadata**。只改元数据，不烧录画面；转码本身仍然离线、硬件加速。

**v1 输入锁定 MP4/MOV/M4V**；MKV 后续版本再评估。这样 v1 不引入 FFmpeg，保持纯 Swift + VideoToolbox 的交付节奏。

## 1. 目标与非目标

### 目标

- 拖入一个或多个视频，批量转码为 H.264 / HEVC / ProRes。
- 默认走 Mac 本地硬件加速，速度优先，CPU 占用低。
- 提供可理解的预设（兼容、均衡、小体积、高质量、剪辑用 ProRes）和自定义参数。
- 队列、进度、速度、剩余时间、取消、重试、失败原因。
- 输出原子落盘：失败/取消不留下半个文件。
- 沙盒 + 安全书签：重启后仍能访问用户授权的输入/输出目录。
- **电影元数据**：勾选“电影”后，转码前从 TMDB 获取元数据；自动匹配必须人工确认，支持重新搜索与手动勘误；元数据写入 MP4/MOV 容器。
- 纯 Swift + SwiftUI；转码离线可用；仅“电影元数据”功能在用户勾选电影时访问 TMDB；无遥测。

### 非目标（v1 不做）

- MKV/AVI/FLV/WMV 输入（v1 不做；MKV 后续版本再评估）。
- AV1/VP9 编码。
- 字幕烧录、字幕轨道封装、多音轨选择。
- Dolby Vision、HDR → SDR 色调映射。
- 电视剧/剧集/动漫的季集元数据（v1 只做电影）。
- 把片名/简介烧录到画面上（v1 只写容器元数据，不改画面）。
- 视频剪辑（裁剪、拼接、滤镜、水印）。
- 网络转码、云端队列、账号系统。
- 直播/录屏/摄像头采集。

## 2. 硬性约束

- **语言**：业务与媒体管线全部 Swift；UI 全部 SwiftUI。
- **系统框架**：AVFoundation、VideoToolbox、CoreMedia、CoreImage、UniformTypeIdentifiers、Observation、Security（Keychain）、CFNetwork（代理常量）。
- **第三方依赖**：0。AppKit 只允许用于 SwiftUI 覆盖不到的最小系统集成（Finder 定位、应用终止清理）；文件选择、拖放优先用 SwiftUI。
- **网络**：仅 TMDB API（P3.6 起可经用户配置的代理，仅作用于 TMDB 请求）；App Sandbox 需要 `com.apple.security.network.client`。API key/token 存 Keychain，不写日志、不硬编码公共 key。
- **TMDB 合规**：设置/关于页展示 “This product uses the TMDB API but is not endorsed or certified by TMDB.”；不使用 TMDB 商标/logo 做应用品牌；遵守 TMDB 速率与缓存条款。
- **最低系统**：macOS 27.0（2026-10-17 由用户拍板：与开发机 / 最新 SDK 对齐，放弃 14.0 兼容代码；原待确认项见第 13 节第 6 条）。开发环境：Xcode 27.1、Swift 6.4、macOS 27.0.1、Apple M1 Pro。
- **硬件加速**：默认 `RequireHardwareAcceleratedVideoEncoder = true`；软件回退只能是用户显式打开的高级选项。
- **分发**：App Sandbox + Hardened Runtime + 公证；App Store 与直接分发共用同一套沙盒配置。

## 3. 支持矩阵

### 输出

| 输出编码 | 容器 | 硬件编码 | v1 | 说明 |
|---|---|---|---|---|
| H.264 | MP4 / MOV | 是 | ✅ | 8-bit 4:2:0 SDR，兼容性最好 |
| HEVC | MP4 / MOV | 是 | ✅ | 8-bit 先做；10-bit/HDR 放 v1.1 |
| ProRes 422 / HQ / LT / Proxy / 4444 | MOV | 是 | ✅ | 剪辑用，体积大 |
| AV1 | — | 否 | ❌ | 当前 VideoToolbox 无编码器 |
| VP9 | — | 否 | ❌ | 无编码器 |

### 输入

- 目标输入：MP4、MOV、M4V。
- 不承诺：MKV、AVI、FLV、WMV、TS、WebM。
- 源视频编码：H.264、HEVC、ProRes 优先；其他编码若 AVFoundation 能解，允许作为输入，但必须通过“硬件解码可用”检查。
- DRM/受保护内容：直接拒绝，并给出明确错误。

### 电影元数据

| 容器 | 元数据写入 | v1 字段 | 说明 |
|---|---|---|---|
| MP4 | iTunes-style metadata | 标题、原名、年份、简介、类型、导演、演员、TMDB ID、海报（可选） | 播放器/系统显示能力不一 |
| MOV | QuickTime metadata | 同上 | ProRes 输出同样可写 |
| M4V | iTunes-style metadata | 同上 | 按 MP4 处理 |

- 只写**容器元数据**，不改画面；不是把片名/简介烧进视频。
- 具体 `AVMetadataIdentifier` 在不同容器/系统版本上支持程度不同；P0 必须做“写入 → 用 AVAsset 读回”验证，不支持的字段降级到 `comment`/`description`。
- 海报是可选增强：TMDB `poster_path` 下载后作为 artwork 写入；写入失败不影响转码，只提示“海报未写入”。

### 画质修复（P7 新增）

- v1 能力：**2x 神经超分 + 强度三档**（轻度/均衡/强力，详见 §7.6）；去噪、锐化、压缩伪影抑制留待后续迭代。
- 输入沿用上表（MP4/MOV/M4V），输出编码/容器不变（H.264/HEVC/ProRes，仍硬件编码）。
- 不承诺：4x 放大、实时处理（ML 超分为离线慢速）、HDR 源（沿用 HDR 拒绝）。
- 模型：内置开源 Real-ESRGAN（BSD-3，经 coremltools 离线转 Core ML）；系统滤镜链（Lanczos + 增强）作为独立「轻量修复」选项与兜底。

### 字幕工具（P8 新增）

- 输入：ASS / SSA / SRT / VTT 字幕文件（文本格式）；不解析容器内挂字幕流（MKV 本就不支持）。
- P8a 质检与适配：时间轴、双语对齐、样式与字体、定位遮挡（静态几何近似）、语法五类规则；**人工确认后**修复，原文件不可变。
- P8b 内容理解：本地 LLM（系统 Foundation Models 框架）做摘要 / 金句提取（带时间戳）/ 角色对白统计；完全离线，不触碰「网络仅 TMDB」约束。
- 不做：字幕生成/识别（Whisper 类已有成熟方案）、字幕烧录进画面（§2 边界不变）、像素级渲染复刻（不内嵌 libass）。

> 已决定：**v1 不做 MKV，后续版本再评估**。这样 v1 不引入 FFmpeg，纯 Swift + VideoToolbox 路线不变。若以后要做 MKV，按下面的方案 B；AV1 输出仍然不支持。

### MKV 支持选项（后续版本）

MKV 是**容器**，不是编码。即使里面是 H.264/HEVC + AAC，AVFoundation/AVAssetReader 也不解析 Matroska；VideoToolbox 只负责编解码，不负责容器。所以“硬件加速”本身解决不了 MKV 输入。

| 方案 | MKV 支持 | 纯 Swift | 硬件加速 | 成本 | 结论 |
|---|---|---|---|---|---|
| A. 纯 Swift 自写 MKV demux | 有限：H.264/HEVC + 部分音频；字幕/附件难 | ✅ | ✅ | 高，2–4 周+，易碎 | 不推荐 v1 |
| B. FFmpeg 只做 demux/解码，VideoToolbox 编码 | 广泛 | ❌ 引入 C 库 | ✅ 视频编码仍硬件 | 中高，2–4 周 | **MKV 硬需求时推荐** |
| C. FFmpeg 全链路 + VideoToolbox 编码器 | 广泛 | ❌ | ✅ | 中，1–2 周 | 可行，但依赖和许可更重 |
| D. 外挂 ffmpeg CLI | 广泛 | ❌ | 取决于参数 | 低 | 打包/沙盒/签名差 |
| E. 用户先手动转 MP4 | 间接 | ✅ | ✅ | 用户麻烦 | 不作为产品方案 |

**推荐 B 的边界**：FFmpeg 只负责读 MKV、拆轨道、时间戳和必要的音频解码；视频解码/编码仍走 VideoToolbox，队列、UI、元数据、落盘全部保持原架构。代价是“纯 Swift”变成“Swift + FFmpeg C 库”，需要处理 LGPL/GPL、动态链接、公证和 App Store 合规。

如果“纯 Swift”是绝对约束，MKV 只能不做，v1 明确只支持 MP4/MOV/M4V。

## 4. 技术路线

### 为什么不用 AVAssetExportSession

`AVAssetExportSession` 只有固定预设，无法精确控制编码器、码率、分辨率、帧率和音频策略。它适合“快速导出”，不适合转码工具。

### 采用 AVAssetReader + AVAssetWriter

- `AVAssetReader` 负责解封装、解码、缩放/旋转/帧率变换。
- `AVAssetWriter` 负责编码与封装；视频编码底层走 VideoToolbox。
- 通过 `AVVideoEncoderSpecificationKey` 指定硬件编码器，并设置 `RequireHardwareAcceleratedVideoEncoder`。
- 快路径：不需要缩放/旋转/变帧率时，用 `AVAssetReaderTrackOutput` 直接读，减少中间渲染。
- 慢路径：需要缩放/旋转/变帧率时，用 `AVAssetReaderVideoCompositionOutput` + `AVVideoComposition`，由系统 GPU 完成变换。

### 输入抽象（为后续 MKV 留缝）

- 引擎只依赖 `MediaSource`：轨道信息 + 按时间顺序的 sample buffer。
- v1 只实现 `AVFoundationSource`（MP4/MOV/M4V）。
- 后续如果做 MKV，新增 `MKVSource` 即可，队列、UI、VideoToolbox 编码、落盘不重写。
- v1 不引入 FFmpeg；这个抽象只是接口边界，不增加运行时代价。

### 何时下沉到 VTCompressionSession

v1 不需要。以下情况再考虑：

- 需要 CBR/多 pass/更精确的码率控制。
- 需要 10-bit HDR 元数据精细控制。
- 需要每帧自定义处理（滤镜、水印）。

代价是要自己处理编码后的 sample buffer 封装，复杂度明显上升。

### 状态流

```
拖入/选择文件
   ↓
MediaInspector（读元数据、判断是否可转）
   ↓
是否电影？
   ├─ 否 → TranscodeJob（快照预设）
   └─ 是 → TMDB 匹配 → 人工确认/勘误
                         ↓
                   TranscodeJob（快照预设 + 元数据快照）
   ↓
QueueStore（排队）
   ↓
TranscodeEngine（串行执行）
   ↓
AVAssetReader → AVAssetWriter(VideoToolbox, metadata)
   ↓
进度/完成/失败 → UI + History
```

### 任务状态机

```
queued → preparing → running → finishing → completed
                  ↘ cancelling → cancelled
                  ↘ failed
```

- `preparing`：加载 asset、校验轨道、检查硬件编码器、检查磁盘、创建临时输出。
- `running`：读写 sample buffer，更新进度。
- `finishing`：`finishWriting`，原子移动到最终路径。
- 失败/取消：删除临时文件，保留错误原因。
- 应用重启时，把上次的 `running` 标记为 `interrupted`，提供重试。
- 电影任务另有 `metadataState`（见 7.5），与转码状态机正交；未 `confirmed` 的任务不会进入执行。

## 6. 核心转码管线

### 6.1 预检

1. 解析安全书签，`startAccessingSecurityScopedResource()`。
2. `AVURLAsset` 加载 `duration`、`tracks`、`isPlayable`、`hasProtectedContent`。
3. 必须有视频轨；音频轨可选。
4. 读取视频轨：尺寸、`preferredTransform`、帧率、码率、颜色参数。
5. 读取音频轨：编码、采样率、声道数。
6. 检测 HDR（PQ/HLG）：v1 拒绝并提示，避免输出偏色。
7. 检测源编码是否有硬件解码器（`VTIsHardwareDecodeSupported`）；没有则拒绝。
8. 检测目标编码是否有硬件编码器；没有则拒绝。
9. 估算输出大小，检查磁盘剩余空间（估算值 + 200 MB 缓冲；目标大小模式以目标大小为下限，ProRes 用标称数据率、质量模式用名义码率；不足则报 `lowDiskSpace`，文案给「预计需要 / 当前可用」）。
10. 生成唯一输出路径，创建同目录临时文件。
11. 如果是电影任务，检查 `metadataState == confirmed` 且 `movieMetadata != nil`；未确认则拒绝开始并打开确认 Sheet。

### 6.2 视频

- 快路径：`AVAssetReaderTrackOutput`，输出 `420v`/`x420` 像素格式。
- 慢路径：`AVAssetReaderVideoCompositionOutput` + `AVVideoComposition`：
  - `renderSize` 目标尺寸；
  - 应用 `preferredTransform` 处理竖屏；
  - 按“适应/填充/拉伸”计算 transform；
  - 默认不放大低分辨率视频；
  - H.264/HEVC 宽高取偶数。
- 帧率：源帧率 / 60 / 30 / 24 / 15；通过 `frameDuration` 或丢帧/复制实现；音频时间轴保持不变。
- 编码设置：
  - `AVVideoCodecKey`：H.264 / HEVC / ProRes；
  - `AVVideoWidthKey` / `AVVideoHeightKey`；
  - `AVVideoCompressionPropertiesKey`：码率控制（三选一，P4）＋关键帧间隔＋期望帧率＋Profile；
  - `AVVideoEncoderSpecificationKey`：硬件编码器 ID + 强制硬件；
  - 颜色属性：BT.709 / BT.601，按源和输出决定。
- 码率控制（设计文档 P4，UI 为「码率控制」三选一）：
  - **平均码率**（默认）：`AVVideoAverageBitRateKey` = 1080p 基准 ×（输出像素数 ÷ 1920×1080），再夹取到预设范围；
  - **质量优先**：`AVVideoQualityKey`（0.05–1.0，默认 0.65），不设码率键；编码器按内容分配码率，输出体积随内容浮动。本机实测硬件 H.264/HEVC 编码器尊重质量键（同为 2 秒 640×360 灰阶噪声：0.9 = 173 KB vs 0.15 = 11 KB，约 15 倍）；体积无法预估，UI 一律标注「按质量推测」，估算用名义码率（`0.25 + 1.75×q²` × 编码 1080p 基准，H.264 8 Mbps / HEVC 6 Mbps），仅用于展示与磁盘预检；
  - **目标大小**：预设存「每个输出文件约 N MB」（十进制，默认 700 MB）；引擎按源时长换算 `视频码率 = N×8÷时长 − 音频码率`，再夹取到预设范围。夹取时在任务提示里说明「目标大小换算码率超出预设范围，已按 X 编码」（实际体积将偏离目标）；时长缺失时回退平均码率并提示。目标大小为输出总大小（含音频），不含容器开销。
- 关键帧间隔（P4）：`AVVideoMaxKeyFrameIntervalKey` = 间隔秒数 × 输出帧率；档位为 自动（2 秒）/ 1 / 2 / 5 / 10 秒，默认自动（与 P2/P3.5 行为一致）。
- Profile（P4）：H.264 可选 自动（High AutoLevel，默认）/ Baseline / Main / High；HEVC 固定 `HEVC_Main_AutoLevel`；ProRes 不适用。
- ProRes（P4）：
  - 仅 QuickTime（MOV）容器；预设层自动归一为 MOV，引擎对「ProRes + 非 MOV」直接拒绝（`proResRequiresMOV`）;
  - 帧内编码：不设码率/质量/关键帧/Profile 键，码率由编码档位（422 / HQ / LT / Proxy / 4444）与输出像素数、帧率决定；
  - 音频用 PCM（见 §6.3）；支持分辨率缩放、帧率只降不升、旋转/竖屏与偶数对齐（与 H.264/HEVC 相同的几何路径）。

### 6.3 音频

- 可直通：AAC/ALAC 输入 → MP4/MOV 输出；PCM → MOV 输出。
- 其他情况重编码：
  - MP4/MOV：AAC-LC 96/128/192/256/320 kbps（320 为系统编码器上限：实测 48 kHz 立体声 320 合法、384 被拒；单声道上限 256 kbps——引擎对单声道 + 320 组合自动夹取到 256 并在任务提示中说明）；
  - ProRes MOV：PCM 16-bit 或 24-bit（预设决定；默认 16-bit）。PCM 不按码率编码，单声道「320 kbps 夹取 256」提示不适用于 PCM；实测 PCM 16/24-bit 立体声 48 kHz 均可被 AVAssetWriter 写入并在读回时得到对应 `mBitsPerChannel`。
- 采样率：源 / 44.1 kHz / 48 kHz（源为 44.1/48 kHz 时保持，其余统一重采样到 48 kHz）。原因：AAC 编码器对不同采样率有各自的合法码率上限（实测 22.05 kHz 立体声上限 128 kbps，预设 192 kbps 会被拒绝），规整后任意预设码率都合法；解码端直接输出目标采样率/声道，保证读写两端格式严格一致。
- 声道：v1 输出单声道/立体声。多声道源（如 5.1）：界面先提示，解码端下混为目标声道数；多轨保留/完整多声道策略 v1.1 再评估。
- 多声道源导致解码与编码声道数不一致（6 声道 LPCM 直送 2 声道 AAC）时同样会被拒绝，故下混必须放在解码端完成。
- 音频不做硬件加速（VideoToolbox 只负责视频）。

### 6.4 进度、取消、落盘

- 读写循环：视频与音频各一个**并发泵**交错写入（`outputProvider.next()` → `inputReceiver.append()`，背压由 append 挂起处理）；单轨串行写完另一轨会让写入器等待交错而永久挂起。
- 进度：视频 PTS / 总时长；无视频轨时用音频 PTS。UI 最多 10 Hz 刷新。
- 速度：已处理媒体秒数 / 墙钟秒数。
- ETA：指数滑动平均，避免数字跳动。
- 取消：`reader.cancelReading()`、`writer.cancelWriting()`，删除临时文件；回调加取消标记，避免 UI 回写。
- 完成：`finishWriting` 成功后，把临时文件移动到最终路径；重名默认加 `-1`，不覆盖。
- 退出/崩溃：下次启动清理 `.chrysalis-*.tmp` 临时文件；中断任务标记 `interrupted`。

### 6.5 元数据

- 非电影任务：保留源的常见元数据（P4 实装）——**标题、作者、创建日期、简介**，其余字段（时长/旋转/颜色参数）由输出媒体本身保证。
  - 读取：`asset.load(.commonMetadata)`，按 `commonKey`（title / artist / author / creator / creationDate / description）匹配。注意实测：`commonMetadata` 条目的 `identifier` 仍是容器写法（如 `itsk/©nam`），归一化信息在 `commonKey` 上，不能按 `commonIdentifierTitle` 匹配。
  - 写入：MP4 → iTunes（©nam / ©ART / ©day / desc）；MOV → QuickTime（title / artist / creationDate / description）。作者取 artist，缺失时回退 author、creator。
  - 自检：写完后按输出容器的 identifier 读回，源里有的字段缺失时报「未保留原元数据：标题」等（已在 MP4→MP4、MP4→MOV 实测）。
- 电影任务：在 `writer.start()` 前设置 `writer.metadata = MetadataWriter.makeItems(...)`；只写已确认的 `MovieMetadata` 快照（此时不叠加源保留字段，电影字段优先）。（部署目标 27.0 起 `startWriting()` 由 `start()` 取代，语义不变。）
- 不承诺：完整章节、所有自定义 metadata、多音轨、字幕轨。
- 输出文件写入后，用 `AVURLAsset` 再读一遍做自检（轨道数、时长、尺寸、编码；PCM 音频检查编码与位深；电影任务额外检查标题/简介是否读回）。

### 6.6 预设参数（P2 / P3.5 / P4）

内置预设如下（默认分辨率/帧率保持源、不放大；P3.5 引入缩档与帧率档位，P4 引入码率控制/关键帧/Profile 与 ProRes）：

| 预设 | 视频编码 | 容器 | 音频 | 1080p 基准码率 | 平均码率夹取范围 |
|---|---|---|---|---|---|
| 兼容优先 | H.264 | MP4 | AAC 192 kbps | 8 Mbps | 2.5–12 Mbps |
| 均衡 | HEVC | MP4 | AAC 192 kbps | 6 Mbps | 2–16 Mbps |
| 小体积 | H.264 | MP4 | AAC 128 kbps | 3 Mbps | 1.5–6 Mbps |
| 高质量 | HEVC | MP4 | AAC 256 kbps | 12 Mbps | 4–40 Mbps |
| 剪辑用 ProRes | ProRes 422 | MOV | PCM 16-bit（可选 24-bit） | 标称 147 Mbps（显示用） | 不适用 |

- 平均码率 = 1080p 基准 ×（输出像素数 ÷ 1920×1080），再夹取到该预设的范围。HEVC 同码率画质优于 H.264（约 25–35% 编码效率），故同等定位下调基准码率。
- 「剪辑用 ProRes」随 P4 提供：ProRes 422 + MOV + PCM 16-bit；卡片显示「ProRes 固定码率（1080p30 ≈ 147 Mbps）」与标称 1 小时体积（按 ProRes 白皮书数据率 × 像素 × 帧率，ProRes 422 1080p29.97 ≈ 147 Mbps / HQ ≈ 220 / LT ≈ 102 / Proxy ≈ 45 / 4444 ≈ 330），不含「夹取范围」。
- 自定义预设编辑字段（P3.5 + P4）：名称、视频编码（H.264 / HEVC / ProRes 422 全家族）、容器（MP4 / MOV）、分辨率档位（保持源 / 2160p / 1440p / 1080p / 720p / 480p）、帧率档位（保持源 / 60 / 30 / 24 / 15 fps）、码率控制（平均码率 / 质量优先 / 目标大小）、关键帧间隔（自动 / 1 / 2 / 5 / 10 秒）、Profile（H.264：自动 / Baseline / Main / High）、音频码率（96 / 128 / 192 / 256 / 320 kbps，非 ProRes）、PCM 位深（16 / 24-bit，ProRes）、采样率（保持源 / 44.1 / 48 kHz）、声道（立体声 / 单声道）；编辑时实时显示体积估算，单声道 + 320 组合给出夹取提示。
- 预设归一（保存时，P4）：ProRes ⇒ 容器强制 MOV、音频强制 PCM（位深缺省 16）、码率控制回退「平均码率」；切回 H.264/HEVC ⇒ 清除 PCM；Profile 仅 H.264 保留，其余编码回退「自动」。
- 预设卡片「预计体积」按所选分辨率档位 · 1 小时估算，标注“预估”。平均码率模式的估算 =（视频目标码率 + 音频码率）× 时长 × 1.05，是**标称值**（按目标码率推导的上界参考），不是对实际文件的预测：实测 5–6 秒真实/合成素材偏差约 −40%～+16%（ABR 编码器按内容复杂度用码率，简单素材系统性偏低），2 秒短视频片段因码率收敛窗口可达 +54%；目标大小模式直接显示「每个文件 ≈ N MB」；质量模式显示名义码率估算并标注「（按质量推测）」；ProRes 显示标称数据率估算。UI 一律用「≈」，见「P3.5 预设编辑增强」的实测记录。
- 用户自定义数值在保存时校验：基准码率 1–40 Mbps（平均码率模式）、质量 0.05–1.0、目标大小 1–100000 MB、PCM 位深 16/24、名称非空且不重名。
- 平均码率模式下，夹取范围随基准码率与来源预设等比缩放；质量优先/目标大小模式不改动夹取范围（目标大小用其作为夹取边界，默认继承来源预设范围）。

## 7. 硬件加速设计（硬性要求）

### 能力检测

启动时调用 `VTCopyVideoEncoderList`，筛出：

- `kVTVideoEncoderList_IsHardwareAccelerated == true`
- `kVTVideoEncoderList_CodecType` 对应 H.264 / HEVC / ProRes

生成 `HardwareCapabilities`：

```
H.264 硬件编码器: Apple H.264 (HW)
HEVC  硬件编码器: Apple HEVC (HW)
ProRes 硬件编码器: AppleProResHW 422 / 422 HQ / ...
```

> 本机实测（M1 Pro / macOS 27.0.1）：`VTCopyVideoEncoderList` 返回 Apple H.264 (HW)、Apple HEVC (HW)、AppleProResHW 422/422 HQ/LT/Proxy/4444；没有 AV1/VP9 编码器。

UI 根据能力矩阵禁用不可用编码；不把“软件编码”伪装成“硬件加速”。

### 强制硬件

视频输出设置中加入：

```swift
AVVideoEncoderSpecificationKey: [
    kVTVideoEncoderSpecification_EncoderID: hardwareEncoderID,
    kVTVideoEncoderSpecification_RequireHardwareAcceleratedVideoEncoder: true
]
```

- 找不到硬件编码器：任务在 `preparing` 阶段失败，错误码 `hardwareEncoderUnavailable`。
- 高级设置提供“允许软件回退”，默认关闭；打开后清除 Require 标志，并在任务上显示 `SW` 警告。
- 不允许静默回退。用户必须知道这次不是硬件加速。

### 解码

- `AVAssetReader` 自动优先硬件解码。
- 预检用 `VTIsHardwareDecodeSupported` 判断源编码；v1 默认要求源视频也能硬件解码。
- H.264 / HEVC / ProRes 源通常满足；MPEG-2/VC-1 等老编码会被拒绝。

### 并发与功耗

- 默认同时只跑 1 个任务；硬件媒体引擎共享，多任务不会线性加速，反而增加内存和热压力。
- 可在设置中允许 2 个并发，但只建议 1080p 以下。
- 转码期间用 `ProcessInfo.beginActivity(options: [.userInitiated, .idleSystemSleepDisabled], ...)` 防止系统休眠；结束/取消时配对 `endActivity`。
- 不在电池电量过低时自动开始大批量任务；v1 只提示，不强制阻止。

## 7.5 电影元数据（TMDB）

### 交互总则

- 只有任务勾选“电影”才触发；默认关闭。非电影任务不联网、不写电影元数据。
- 流程固定为：**勾选电影 → 自动匹配 → 人工确认/勘误 → 确认后才能开始转码**。
- 自动匹配结果永远不静默写入；即使是高置信度，也必须经过一次明确确认。
- 未确认的电影任务会拦截“开始全部”，并跳转到待确认列表。
- 元数据是任务快照；转码开始后修改元数据，不影响正在写的输出。

### 状态机

```
none → searching → needsReview → confirmed
                  ↘ failed → needsReview
confirmed → editing → confirmed
```

- `none`：未勾选电影，或尚未请求。
- `searching`：正在请求 TMDB。
- `needsReview`：已有候选/预填字段，等待用户确认。
- `confirmed`：用户确认，可以转码。
- `failed`：网络/API 错误；可重试，也可直接手动填写。
- `source` 记录 `tmdb` / `manual`，历史里能看出是自动匹配还是人工填写。

### 文件名解析与匹配

1. 去扩展名；`.`、`_` 替换为空格；去掉常见发布组、分辨率、编码、音轨、片源标记（1080p、2160p、4K、BluRay、WEB-DL、HDR、x265、HEVC、DDP、AAC、REMUX 等）。
2. 提取年份 `(19|20)\d{2}`；年份前作为主标题；括号内容作为备选标题。
3. 先按“标题 + 年份”搜索；无结果再去掉年份、用主标题搜索；仍无结果时让用户手动改关键词。
4. TMDB 搜索只取前 5 个候选；评分考虑标题精确度、年份、原始标题、热度。
5. 高置信度候选可以预填，但状态仍是 `needsReview`，不自动确认。
6. 用户可点“换一个”浏览候选，或“手动填写”完全自定义。

### TMDB API

- 使用 `URLSession` + `Codable`，不引入第三方 SDK。
- 支持 v3 API Key 或 v4 Read Access Token；用户在设置里填写，存 Keychain，不写日志、不硬编码公共 key。
- 设置页“验证”调用 `GET /3/configuration`（v3 key）或 `GET /3/movie/550`（v4 token）；401 直接提示 key 无效。
- 代理（P3.6，2026-10-19 走查反馈）：国内直连 `api.themoviedb.org` / `image.tmdb.org` 常不可达；设置页「网络代理」分组可配置 HTTP/HTTPS 或 SOCKS5 代理（默认 `127.0.0.1:7890`，对齐 Clash 等本地客户端），存 UserDefaults（非机密）。经 `URLSessionConfiguration.connectionProxyDictionary` 下发，搜索/详情/海报/凭据验证全部走代理会话；设置变化自动重建会话，即时生效。未启用时遵循系统代理设置；v1 不支持代理用户名/密码认证。
- 「测试连接」按钮：请求 `/3/configuration`（伪 Key），401/429 视为已到达 TMDB；失败给出中文原因。
- 主要端点：
  - `GET /3/search/movie?query={title}&year={year}&language=zh-CN&include_adult=false`
  - `GET /3/movie/{id}?language=zh-CN&append_to_response=credits,release_dates`
- 读取字段：`title`、`original_title`、`release_date`、`overview`、`genres`、`runtime`、`vote_average`、`poster_path`、`credits.crew`（导演）、`credits.cast`（前 10 位）、`imdb_id`。
- 海报：`https://image.tmdb.org/t/p/w342{poster_path}`，URLSession 下载并缓存；失败只提示，不阻塞。
- 语言默认 `zh-CN`，可切 `en-US`；保留 `original_title`。
- 速率与缓存：请求串行化 + 300ms 防抖；遵守 429 `Retry-After`；搜索/详情缓存 7 天；提供“清除元数据缓存”。
- 错误分类：未配置 key、401、429、超时、无结果、解码失败；每种都要有可执行下一步（去设置/重试/手动填写）。
- 隐私：只有勾选电影时才把文件名/标题发给 TMDB；设置页明确说明；API key 不进入日志。

### 勘误 UI

- 一个 720px 宽的 Sheet：左侧候选列表（海报、标题、年份、简介两行），右侧可编辑表单。
- 字段：标题、原名、年份、上映日期、简介、类型、导演、演员、TMDB ID、海报预览。
- 操作：重新搜索、使用此结果、手动填写、确认并用于转码。
- 用户一旦手动修改，标记“已手动修改”；重新搜索不得静默覆盖，必须二次确认。
- 校验：标题非空；年份 1888…当前年份+2；简介/演员允许为空；TMDB ID 可空。
- 海报可选：下载失败不阻塞，只显示“海报未获取”。

### 写入视频

- `TranscodeRequest` 增加 `metadata: MovieMetadata?`；`TranscodeSession` 在 `writer.start()` 之前设置 `writer.metadata`。
- 字段映射（优先容器原生 identifier，失败再降级到 comment/description）：

| 字段 | MP4（iTunes） | MOV（QuickTime） | 降级 |
|---|---|---|---|
| 标题 | Title | Title | 必写 |
| 原名 | — | — | `Comment: Original Title: ...` |
| 年份/上映日期 | Release Date | Creation Date | ISO 8601 字符串 |
| 简介 | Description | Description | Comment |
| 类型 | Genre | Genre | Comment |
| 导演 | Artist | Artist | Comment |
| 演员 | — | — | `Comment: Cast: ...`（前 5 位） |
| TMDB ID | — | — | `Comment: TMDB: ...` |
| 海报 | Artwork | Artwork | 可选，失败不阻塞 |

- 具体 `AVMetadataIdentifier` 在 P0 用 `AVAssetWriter` 实测；不支持的字段不要假装写入。
- 写完后用 `AVURLAsset` 读回验证标题/简介等关键字段；缺失时给“元数据写入不完整”警告，但输出文件仍保留。
- 非电影任务不设置 `writer.metadata`，不引入额外字段。

> **P0 实测修正（2026-10-17）**：本表字段映射按容器落地如下——MP4 用 iTunes 写法：标题 `©nam`、简介 `©des`、上映日期 `©day`（`YYYY-MM-DD`）、类型 `©gen`、导演 `©dir`、原名/演员/TMDB `©cmt`、海报 `covr`（需 `keySpace=.iTunes + key="covr"`，`.commonIdentifierArtwork` 无效）；MOV 用 QuickTime 写法：`mdta:title/description/creationdate/genre/director/comment/artwork`（年份用 ISO 8601 写入 `creationdate`）。`quicktime.*`（mdta）identifier 写到 MP4 会被静默丢弃，反之 iTunes 写法在 MOV 可用。MP4 组合写入（8 字段）与 MOV 组合写入（7 字段）均读回 100%。详见 [`P0-实测报告.md`](P0-实测报告.md) 第 6 节。

## 7.6 画质修复（ML 超分，P7）

> 2026-10-19 新增需求，用户拍板三项：**技术主线 Core ML + 系统滤镜兜底；模型内置开源（Real-ESRGAN，BSD-3）；v1 单能力打通（2x 超分 + 强度三档）**。输出端仍走 VideoToolbox 硬件编码，本节不触碰 §2 硬性约束（零第三方**代码**依赖不变：模型是资产而非代码库；不引入 FFmpeg/推理库）。
>
> **2026-10-21 P7.1 后拍板：双模式**——**快速档** `realesr-general-x4v3`（0.5x 预降采样 + 4x，352×288 tile，约 0.138x）；**精细档** `RealESRGANv2-animevideo-xsx2`（原生 2x，384×384 tile，约 0.060–0.074x）。4K 源允许 8K 输出，但 P7.2 必须先探测硬件编码器；不支持时在 preparing 阶段明确失败，不静默降级。

### 范围与定位

- v1 单能力：**2x 神经超分 + 强度三档**，神经模式内含**快速（通用）/ 精细（动画）**两档模型；去噪/伪影抑制为后续迭代。
- 画质修复是**任务级开关**（与转码预设正交）；开启神经超分时分辨率档位锁定「保持源」并禁用，输出尺寸 = 源显示尺寸 × 2（偶数对齐，只放大不缩小），避免档位与超分的组合爆炸。快速档内部先降半分辨率再 4x，但对外输出仍是源尺寸 ×2。
- 输出编码/容器/音频/元数据逻辑全部沿用现有预设；任务可与其他转码任务混排。
- 4K 源输出 8K：允许，但需 P7.2 编码器探测通过；吞吐极低（快速档约 0.03–0.04x，精细档更低），UI 必须如实显示 ETA 与慢速警告。

### 技术路线

| 层 | 选择 | 说明 |
|---|---|---|
| 主线 | Core ML + ANE，双模型 | Real-ESRGAN（BSD-3）→ coremltools 离线转 `.mlpackage`（fp16）→ 打包 `.mlmodelc`；快速档 `realesr-general-x4v3`（4.7 MB，半分辨率 4x），精细档 `RealESRGANv2-animevideo-xsx2`（2.3 MB，原生 2x）；`MLModelConfiguration.computeUnits = .all`（ANE 优先，GPU/CPU 兜底执行），用 `MLComputePlan` 查询实际执行设备并在检查器展示 |
| 兜底 | CoreImage 滤镜链 | Lanczos 放大 + 细节增强/锐化/降噪组合；既是独立「轻量修复」选项，也可在用户显式开启时替代模型（与软件编码回退同构：默认关、不静默、开启后显示提示） |
| 不采用 | 自研 Metal kernel / 第三方推理库 | 前者效果上限低、工作量不小；后者违反零依赖 |

### 管线架构

- `TranscodeRequest` 增加 `enhancement: EnhancementSetting?`（`mode: neural / filter`，`neuralModel: fast / fine`（仅 neural 有效），`strength: light / balanced / strong`）。
- 引擎读端之后插帧处理层 `FrameEnhancer` 协议：`CVPixelBuffer → CVPixelBuffer`；三实现：`NeuralUpscaler`（Core ML，按 `neuralModel` 选模型）、`FilterUpscaler`（CI 滤镜链）、`Passthrough`（关闭）。管线：reader 输出像素 → 增强层 → writer。P7.1 探针用 BGRA；集成时在增强层入口/出口做 420f↔BGRA 转换（具体转换点由 P7.2 实测，优先 vImage/Core Image 零拷贝或像素缓冲池）。
- **tile 策略**：放大后长边 > 2048 像素的帧切 tile，重叠 32px、羽化混合。P7.1 实测：**精细档 384×384**（1080p 18 tiles）；**快速档 352×288**（960×540 6 tiles，16:9）；非 16:9/竖屏源允许回退 352×352 或 384×384，P7.2 按画面比例选。1080p 及以上（2x 后长边 3840）必走 tile；内存不是瓶颈（maxrss <216 MB），瓶颈是 ANE tile 效率。
  > **2026-10-21 修正**：原文「1080p 源整帧推理」与「长边 >2048 切 tile」矛盾；以 tile 阈值为准。P7.1 实测 512×512 不是最优（compact 384×384、general 352×288 更快）。
- 时间戳、音频直通逻辑不变；进度按帧推进，EMA 估 ETA（处理慢，预估必须如实展示）。
- 强度三档共用同一次推理，不重复计算。两档模型的默认后处理不同：
  - **精细档**：轻度 = 模型输出与原图 Lanczos 2x 按 alpha ≈ 0.4 混合；均衡 = 纯模型输出；强力 = 模型输出 + 后置 USM。
  - **快速档**：轻度 = 模型输出与原图 Lanczos 2x 按 alpha ≈ 0.4 混合（补回部分真实细节）；均衡 = 纯模型输出 + 轻度 USM（补偿半分辨率 4x 的偏软）；强力 = 模型输出 + 更强 USM。
  - USM 半径/强度由 P7.4 在真实片源上调参；默认值需可复现并写入设置。

### 模型管理

- 转换脚本入 git（`Validation/Models/`，Python + coremltools，仅离线使用、不进 App）；模型产物 `.mlpackage/.mlmodelc` 不入 git（见 §13-14 待确认），构建前本地生成后放进 App Resources。
- App 启动**懒加载**模型：只加载用户选中的那一档；首次使用时校验（输入/输出形状、模型标识）并记录执行设备；加载失败 → 任务在 preparing 阶段失败（人话提示：模型缺失或损坏），**不静默回退**滤镜链。
- 关于页 attribution 注明两个模型名、来源与 BSD-3 许可。
- 已转换并验证：`RealESRGANv2-animevideo-xsx2`（原生 2x，2.3 MB，动画调优）、`realesr-general-x4v3`（通用 4x，4.7 MB，半分辨率快路径）；x2plus 因 0.010x 不采纳。两模型合计约 7 MB，均随 App 打包（本地生成后放入 Resources）。
- 8K 编码器探测：P7.2 在 preparing 阶段对目标容器/编码器/分辨率调用 VideoToolbox 能力探测；不支持 8K 时任务失败并给出「当前编码器不支持 8K，请改用 4K 源或关闭神经超分」人话提示，不静默降到 4K。

### 性能预算（P7.4 实测后修订）

| 场景 | 目标 |
|---|---|
| 1080p 2s 片端到端 | 成功、硬编码命中、tile 无接缝（两档模型都测） |
| 1080p30 超分吞吐（快速档） | **≥ 0.1x 实时**（1 分钟片 ≤ 10 分钟） |
| 1080p30 超分吞吐（精细档） | 不承诺 0.1x；M1 Pro 约 0.060–0.074x，UI 如实显示 ETA 与慢速提示 |
| 4K tile 内存峰值 | < 1.5 GB |
| 滤镜链兜底吞吐 | ≥ 1x 实时（GPU） |
| 4K 源 → 8K 输出 | 编码器探测通过才允许；快速档约 0.03–0.04x，精细档更低，必须显示慢速警告 |

> **P7.1 实测（M1 Pro，2026-10-21，已拍板双模式）**：快速档「通用 4x + 0.5x 预降采样 + 352×288 tile」模型 0.146–0.149x，加预降采样 + 轻度 USM 估算 0.138x；精细档 compact 原生 2x 0.060–0.074x，未达 0.1x。内存全部 <216 MB。x2plus 仅 0.010x，int8/GPU-only/并发/batch 均无收益。详见 `docs/P7-实测报告.md`。
>
> **8K 拍板**：允许 8K 输出，但 P7.2 必须先探测 H.264/HEVC/ProRes 的 8K 能力；不支持则 preparing 失败并说明，不静默降级。4K 源吞吐极低（快速档约 0.03–0.04x），UI 必须显示 ETA 与「4K→8K 超分很慢」提示。

### 验收

- 单帧：快速/精细两档分别加载 → 推理 → 输出尺寸 = 输入 ×2、格式正确；快速档内部 0.5x 预降采样不影响对外尺寸。
- tile：合成渐变/条纹片，两种 tile（384×384 / 352×288）接缝差值在阈值内（harness 用例）；竖屏/非 16:9 回退路径不崩。
- 端到端：2s 合成片 → 两档模型分别超分转码成功 → 输出尺寸翻倍 → 硬件编码命中 → 无临时残留；快速档 1080p30 ≥0.1x，精细档记录实测值并显示慢速提示。
- 兜底：滤镜链端到端成功；模型缺失/形状不符明确失败不静默；选中精细档不会误加载快速档。
- 8K：编码器探测通过时允许 4K→8K 任务（至少验证 preparing/写入端不会静默降级）；不支持时明确失败；不得把 8K 静默降成 4K。
- 性能：上表实测记录进 `docs/P7-实测报告.md`（P7.4 更新）。

## 7.7 字幕工具（P8）

> 2026-10-19 立项。用户拍板四项：**扩展字幕模块（侧边栏新页）；先质检适配（P8a）后内容理解（P8b）；本地 LLM 用 Foundation Models（系统框架）；ASS 适配采用静态几何近似**。字幕功能完全离线，不触碰「网络仅 TMDB」约束；不引入 libass 等第三方解析/渲染库。

### 范围与定位

- **P8a 字幕质检与适配**：批量检测 ASS/SSA/SRT/VTT 的结构与排版问题，人工确认后自动修复。定位「小而痛」的确定性问题，纯规则引擎。
- **P8b 内容理解**：基于 Foundation Models 的分集摘要、金句提取（带时间戳）、角色对白统计。定位差异化新意，依赖系统模型可用性。
- 不做：字幕生成/识别（Whisper 类已有 srtforge、SmartSub 等成熟方案）、字幕烧录进画面、视频切片/跳转（剪辑禁区不变）、像素级渲染复刻。
- 产品形态：侧边栏新增「字幕」模块（与队列/历史/设置并列）；字幕文件独立列表，与视频转码任务互不耦合。

### P8a 质检与适配

**解析**（纯 Swift 自研，零依赖）：

- 格式：ASS/SSA（`[Script Info]` / `[V4+ Styles]` / `[Events]` + override tags 子集：`\pos` `\move` `\an` `\fn` `\fs` `\fad` 等）、SRT、VTT。
- 编码探测：BOM → UTF-8 严格校验 → GBK 回退，失败明确报错。
- 语义模型：事件（时间轴、文本、样式、定位）、样式表、脚本信息；供质检与修复共用。

**质检规则**（报告分级：错误 / 警告 / 提示）：

| 类别 | 规则 |
|---|---|
| 时间轴 | 同轨重叠超限、时间倒挂、零时长、间隔过短、阅读速度 CPS 超标（默认阈值 20，可调） |
| 双语 | 主行/译行行数不对齐、时间偏移超阈值、次序颠倒 |
| 样式 | 引用不存在的 Style、系统缺失字体（`NSFontManager` 探测）、按字号估算的行宽过长、字号过小 |
| 定位 | `\pos`/`\move`/margin/对齐 → 静态几何区域，同时间轴多行区域重叠（遮挡近似）、画面出界 |
| 语法 | 大括号/括号不配对、override tag 未闭合、空行、编码异常 |

**修复**（全部经人工确认后执行，沿用「永不静默写入」与原子落盘惯例）：

- 可自动修复：时间轴重叠合并/倒挂修正、双语微移对齐、长行按标点/词界拆分、双语行合并。
- 仅告警 + 建议（不自动改写）：CPS 超标（建议时长，避免语义漂移）、字体缺失（给出系统可用的回退字体建议，替换需确认）。
- 输出：原子写盘；**不覆盖原文件**（默认生成 `-fixed` 副本）；修复后自动重新质检，可修复类规则应归零。
- **播放器适配声明**：IINA（libass）/Infuse/QuickTime 的实际渲染无法本地复刻；P8a 交付静态规则 + 「播放器适配走查清单」，像素级效果由用户按清单实机核对。

### P8b 内容理解（Foundation Models）

- 依赖：`SystemLanguageModel`（macOS 26+，Apple Silicon + Apple Intelligence 启用）。availability 三态：**可用** / **未启用 Apple Intelligence**（展示引导，不报错）/ **设备不支持**（模块入口隐藏）。三态都不影响转码主功能。
- 能力：
  1. **摘要**：字幕按时间窗分块 → 逐块摘要（Map）→ 汇总（Reduce），控制在系统每日 token 预算内，进度可见。
  2. **金句提取**：`@Generable` 结构化输出（原文 + 起止时间戳 + 类型标签）；**原文精确匹配校验**——提取文本必须在字幕原文中命中，未命中直接丢弃（防幻觉）。
  3. **对白统计**：优先 ASS 说话人标记/样式名；无标记时 LLM 推断并标注置信度。
- 出口（v1 默认）：Markdown 报告（摘要 + 金句时间戳列表 + 对白统计），金句列表可复制；更多出口待确认（§13-15）。
- 隐私：全程本地推理，无任何网络请求；设置页说明。

### 验收

- 解析器：三种格式往返解析 + 异常容错（harness 单元测试）；1000 行 ASS 解析 < 1s。
- 质检：逐规则构造问题样例验证；修复后重新质检，可修复类归零；原文件字节不变。
- P8b：availability 三态行为正确；金句时间戳全部可对齐原文字幕；验证无网络请求。
- 修复流：报告 → 选择规则 → 确认 → 原子落盘 → 重新质检，全程可取消。

## 8. UI / UX：极简、科技感、顺手

### 8.1 设计原则

1. **暗色优先，跟随系统**：深空灰底 + 单一冷色强调；浅色模式同样克制。
2. **一屏一个主操作**：主按钮只有一个（开始/继续），其他操作降级为图标或次级按钮。
3. **用留白和细线建立层次**：不用满屏卡片、阴影、渐变；分隔线 1px。
4. **科技感来自精度**：等宽数字、状态点、细线、克制的光；不靠霓虹、玻璃、粒子背景。
5. **原生 macOS 优先**：保留 traffic lights 和原生 toolbar，不做假标题栏；控件用系统行为。
6. **信息密度**：队列行 56–64px，一屏至少 8 行；检查器默认隐藏，需要时再出现。

### 8.2 视觉系统

| Token | Dark | Light | 用途 |

| `surfaceElevated` | `#171C22` | `#FFFFFF` | 检查器、浮层、Toast |

| `textSecondary` | `#8A94A2` | `#5D6775` | 元信息、说明 |
| `accent` | `#5BE1FF` | `#007C91` | 主按钮、进度、选中态 |

- 暗色模式不用纯黑 `#000`，浅色模式不用纯白铺底；避免刺眼和“网页感”。

### 8.5 动效

- Hover 120ms、选中 180ms、检查器滑入 220ms、Toast 300ms；统一 `easeOut`。

- 进度线用线性更新；数字用等宽字体，避免宽度抖动。

**队列页**

## 9. 数据与持久化

v1 用 `Codable` JSON + `UserDefaults`，不引入 SwiftData，避免迁移成本。

- `Settings`：JSON 存 `UserDefaults`。
- `PresetStore`：内置预设写在代码里；自定义预设存 `Application Support/Chrysalis/presets.json`。
- `QueueStore`：活动队列存 `queue.json`；启动时恢复，运行中任务改为 `interrupted`；电影任务连同 `MovieMetadata` 快照一起保存。
- `HistoryStore`：`history.json`，最多 500 条；电影记录保留元数据快照，便于重新转码/查看。
- `BookmarkStore`：输入文件、输出目录的安全书签（`withSecurityScope`），Base64/Data 存入模型。
- `KeychainStore`：TMDB API Key / Read Token；不进入 JSON、不进入日志。
- `MetadataCache`：TMDB 搜索/详情响应缓存 7 天，存 `Caches/Chrysalis/TMDB/`；海报缓存存 `Caches/Chrysalis/Posters/`；可一键清除。
- 缩略图：`Caches/Chrysalis/Thumbnails/`，按文件 URL + 修改时间缓存；可随时清理。
- 模型：`TranscodeJob` 增加 `mediaKind`、`metadataState`、`movieMetadata`；`MovieMetadata` 含 `tmdbID/title/originalTitle/year/releaseDate/overview/genres/director/cast/posterURL/source/isConfirmed`。

## 11. 验收与测试

> P6 起测试与基准统一由 `Validation/Harness` 执行（零第三方依赖 SwiftPM 包；`Core/` 为指向应用源码的目录符号链接，随 git 入库）：
> `cd Validation/Harness && swift run check [all|unit|integration|bench|list]`。
> 不建 Xcode 测试 Target（工程为文件系统同步组，避免手拼 pbxproj）；测试片用 AVAssetWriter 现场生成，仓库不放大文件。

### 单元测试

- 码率计算：目标大小、音频扣除、边界、零时长。
- 码率规划（P4）：平均码率缩放/夹取、质量名义码率（单调、0.65 ≈ 基准）、ProRes 标称数据率（像素/帧率线性）、PCM 标称码率。
- 输出路径：重名、非法字符、扩展名、目录不存在。
- 预设解析：编码/容器/音频组合校验；P4 新字段 JSON 往返与旧 JSON 缺省兼容。
- 预设校验与归一（P4）：ProRes ⇒ MOV + PCM、质量/目标大小边界、平均码率模式缩放夹取范围、目标大小模式不缩放。
- 任务状态机：合法/非法迁移，重启恢复。
- 文件名解析：年份、分辨率/编码/发布组剥离、中文/英文标题、无年份。
- 匹配评分：精确标题+年份、同名不同年、原始标题、低置信度。
- 元数据校验：空标题、非法年份、脏字段、手动修改标记。
- 开始前置校验：电影未确认时拒绝开始。
- TMDB 解码/错误：401、429、超时、空结果、无 key。
- 时间/大小格式化。

### 集成测试

用 AVAssetWriter 在测试里生成 2 秒测试片，避免仓库里放大文件。

- H.264 + AAC → H.264 + AAC MP4。
- HEVC + AAC → HEVC + AAC MP4。
- H.264 → ProRes 422 MOV（PCM 16-bit / 24-bit，读回 LPCM 与位深）。
- 竖屏 transform（输出尺寸摆正、transform 归一为 identity、走旋转慢路径）。
- 质量优先：输出成功且体积随质量单调（0.9 > 0.15）。
- 目标大小：换算成功 / 夹取提示两种路径。
- 磁盘预检：超大目标直接 `lowDiskSpace`，不产生临时文件。
- 无音频轨。
- 取消：输出不存在，临时文件不存在。
- 重名：生成 `-1` 后缀。
- 无硬件编码器：`XCTSkip` 或期望错误。
- 电影元数据写入 MP4，读回标题/年份/简介/类型。
- 电影元数据写入 MOV，读回标题/简介。
- 电影任务同时应用转码参数（720p + 关键帧 + 元数据）。
- 非电影任务不写电影字段；保留源标题/作者/创建日期（MP4→MP4 的 itsk 写法、MP4→MOV 的 QuickTime 写法）。
- 元数据字段不支持时降级到 comment，不导致转码失败。

### 手工矩阵

- iPhone 4K HEVC、竖屏、HDR（v1 应拒绝/提示）。
- 29.97 / 59.94 / 60 fps。
- VFR 源。
- 5.1 音频（v1 警告）。
- 中文/emoji 文件名。
- 外接硬盘、低磁盘空间。
- 长视频（>30 分钟）。
- 转码中退出 App、强制结束、重新打开。
- 输出目录被删除/无权限。
- 电影自动匹配错误 → 手动搜索/编辑 → 确认 → 转码。
- 批量混合电影/非电影；电影未确认时“开始全部”被拦截。
- 无 TMDB key、断网、401、429、TMDB 返回空结果。
- 同一电影中英文标题、年份歧义、系列电影。
- 海报下载失败仍能确认并转码。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 用户要求 MKV/AVI/FLV/WMV 输入 | 纯 Swift 路线不成立 | 开工前确认；若必须支持，放宽到 FFmpeg 或自写解封装 |
| 用户要求 AV1/VP9 输出 | VideoToolbox 无编码器 | 明确不支持；不要承诺 |
| HDR/杜比视界 | 输出偏色/失败 | v1 检测并拒绝；v1.1 做 HEVC 10-bit HDR 保留，再做色调映射 |
| 字幕烧录/封装 | AVFoundation 支持有限 | v1 不做；后续用 AVVideoComposition + Core Graphics 渲染 |
| 目标大小不精确 | 用户预期落差 | 目标大小按「MB/文件」存预设，引擎按时长换算并扣音频、按预设范围夹取（夹取时中文提示）；标注“预估”，接受内容相关偏差（P3.5 实测 −40%~+55%，简单素材偏低、短视频收敛不足）；不做双 pass 承诺 |
| 质量优先体积不可预估 | 用户预期落差 | `AVVideoQualityKey` 由编码器按内容分配码率（实测 0.9 vs 0.15 体积约 15 倍）；UI 标注「按质量推测」，卡片只给名义码率估算，不承诺体积 |
| 硬件编码器不存在 | 老 Intel Mac 无法转码 | 能力矩阵禁用；高级选项允许软件回退 |
| ANE 超分性能不达标（<0.1x 实时） | 修复耗时过长，用户流失 | 小参数量模型 / tile 优化；滤镜链「轻量修复」提供快路径；UI 如实预估处理时长 |
| tile 接缝可见 | 画面竖纹 | 重叠 32px 羽化混合；合成片差值检查进 harness |
| 模型体积与许可 | 包体膨胀 / 合规风险 | fp16 量化；BSD-3 attribution；产物不入 git（§13-14） |
| 无 ANE 机型（Intel / 老 M 芯片） | 超分速度大幅下降 | `computeUnits = .all` 自动落 GPU/CPU；检查器如实展示执行设备 |
| ASS 渲染近似误差 | 修复后实际播放器仍有排版问题 | 静态几何近似 + 播放器适配走查清单；文档明确不承诺像素级一致 |
| Foundation Models 不可用 / 每日预算受限 | P8b 功能不可用 | availability 三态优雅降级；分块摘要控制预算；不可用时隐藏入口不报错 |
| LLM 幻觉（金句不存在） | 输出内容不可信 | 提取文本强制原文精确匹配校验，未命中丢弃 |
| 字幕编码异常（GBK/无 BOM） | 解析失败或乱码 | BOM → UTF-8 严格校验 → GBK 回退的探测链，失败明确报错 |
| TMDB 自动匹配错误 | 视频被写入错误片名/简介 | 高置信度也只预填，必须人工确认；提供候选/手动勘误；未确认阻止开始 |
| TMDB API key/条款 | 无法请求或被限流 | 用户自带 key 存 Keychain；不硬编码公共 key；缓存、防抖、遵守 429；设置页署名 |
| 元数据字段容器不支持 | 写了但播放器不显示 | P0 用 AVAssetWriter 写入/读回验证；不支持字段降级到 comment；输出后自检 |
| 隐私：文件名发给 TMDB | 用户不知情 | 只有勾选电影才联网；设置页说明；不记录 key/请求正文 |
| 网络不可用 | 电影流程阻塞 | 保留“手动填写”路径；转码本身不依赖网络 |
| 海报写入失败 | 元数据不完整 | 海报可选，失败只提示，不阻塞转码 |
| Swift 6 并发 + AVFoundation 非 Sendable | 编译/运行时问题 | 引擎隔离在专用串行队列；`@preconcurrency import AVFoundation`；事件用简单值类型 |
| 沙盒书签失效 | 重启后无法读文件 | 启动时解析并校验；失效则要求重新选择 |
| 长时间转码发热/降频 | 速度下降 | 单任务默认；显示速度；不承诺固定时长 |
| App Store 审核 | 被拒风险 | 无私有 API、无下载可执行代码、沙盒、公证 |

## 13. 待确认

1. **输入格式**：**已决定：v1 只支持 MP4/MOV/M4V；MKV 后续版本再评估，不引入 FFmpeg。**
2. **输出编码**：是否必须 AV1/VP9？当前 Mac 硬件编码不支持。
3. **HDR**：v1 是否必须处理 HDR/杜比视界？建议 v1 先拒绝，v1.1 再做。
4. **字幕**：是否需要烧录或保留字幕轨？v1 默认不做。
5. **分发**：App Store 还是官网 DMG？两者都按沙盒 + 公证设计。
6. **最低系统**：**已决定：macOS 27.0**（2026-10-17 用户拍板；放弃 14.0 兼容代码，与开发机和最新 SDK 对齐）。
7. **界面语言**：先中文，还是中英双语？
8. **批量优先还是单文件优先**：本计划按“批量优先”设计；如果只是偶尔转一个文件，UI 可以更简。
9. **元数据形式**：确认是写容器元数据（QuickTime/iTunes），不是把片名/简介烧进画面？
10. **TMDB Key 来源**：v1 按“用户自带 key/token”设计；是否接受？如果要开箱即用，需要后端代理并遵守 TMDB 条款。
11. **海报**：v1 是否必须写入海报？计划里是可选增强，失败不阻塞。
12. **元数据语言**：默认 `zh-CN`，是否需要在设置里切 `en-US`？
13. **剧集**：v1 只做电影；电视剧/动漫的季集元数据是否后续再加？
14. **画质修复模型的存储方式**（2026-10-19 P7 立项）：已决定模型内置（开源 Real-ESRGAN，BSD-3）；转换脚本入 git、`.mlpackage/.mlmodelc` 产物**默认不入 git**（构建前本地生成）——是否改为模型文件入库（仓库 +几十 MB）待确认。
15. **字幕金句/摘要的出口形态**（2026-10-19 P8 立项）：默认 Markdown 报告 + 金句可复制；是否需要更多出口（章节文件、分享卡片等）待确认。
